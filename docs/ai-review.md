# Ревью billing.py с помощью ИИ

Инструмент: Claude Code (Claude Sonnet).

На ревью отдавался вариант после первого исправления (коммит "Исправлено: округление минут вверх..."):

```python
def calculate_cost(duration_seconds):
    if duration_seconds < 0:
        raise ValueError("duration_seconds must be >= 0")
    minutes = -(-duration_seconds // 60)  # округление вверх без float
    return 50 + minutes * 8
```

## Что нашёл ИИ и что с этим сделано

**1. Магические числа 50, 8 и 60.** Тариф прямо в коде, чтобы поменять цену, надо лезть в формулу. В документации к лабе 8 цена уже описана как настройка (`START_FEE`, `PER_MINUTE`).
Решение: принято, это как раз то, что просили проверить в задании. Сделано: класс `Tariff`, тариф по умолчанию `DEFAULT_TARIFF`, функция `tariff_from_env()`, а 60 стало константой `SECONDS_IN_MINUTE`.

**2. Деньги в int / float.** Если цена минуты будет 7,5 руб., int не подойдёт, а float даёт ошибки округления (известное `0.1 + 0.2 != 0.3`).
Решение: принято. Тариф и результат теперь `Decimal`, цена округляется до копеек.

**3. nan и inf.** `nan < 0` даёт False, проверка пропускает его, и в цене получается `nan`. С `inf` цена бесконечная.
Решение: принято. Добавлена проверка `math.isfinite` и тесты.

**4. True и строки.** `calculate_cost(True)` считается как 1 секунда, потому что bool в Python - это число. На строке `"60"` падает с непонятной ошибкой внутри формулы.
Решение: принято. Теперь явная проверка типа, для bool и не чисел понятный `TypeError`.

**5. Деление через float может врать на границах** (типа `3.0000000000000004`).
Решение: для целых секунд это уже было решено целочисленным делением, но чтобы работали и дробные секунды, использован `Fraction`. Он делит точно.

**6. Нет аннотаций типов и docstring.**
Решение: добавлены.

**7. Ограничение на длину поездки, например 24 часа.**
Решение: не принято. В задании такого нет, тариф в лабе 8 без ограничений. Если кто-то правда катался долго, лучше посчитать цену, чем выдать ошибку. Такие ограничения должен решать владелец продукта, а не функция расчёта.

**8. Отрицательный тариф в настройках** (`PER_MINUTE=-1`) даст отрицательную цену.
Решение: принято. Проверка в `Tariff` и тест.

**9. Если в переменной окружения не число**, `tariff_from_env` падает с `decimal.InvalidOperation`.
Решение: частично. Оставлено как есть: лучше сразу упасть при неправильной настройке, чем тихо взять значение по умолчанию. Можно было бы только сделать сообщение понятнее.

## Где ИИ ошибся ещё до ревью

Первый черновик был такой: `minutes = round(duration_seconds / 60)`. Из 7 тестов 4 упали:

- `round()` округляет до ближайшего, а нужно вверх. 17 минут 10 секунд = 17 минут = 186 руб. (а надо 194), 1 секунда = 0 минут = 50 руб. (а надо 58);
- ещё у `round()` в Python банковское округление: `round(0.5) == 0`, `round(2.5) == 2`;
- не было проверки на отрицательное время.

Тесты писались по условию задачи, а не под код, поэтому ошибку поймали сразу.

## Что в итоге

- 30 тестов, покрытие `billing.py` 100%.
- Основные случаи считаются так же: 0 секунд = 50 руб., 17:10 = 194 руб., 6 часов = 2930 руб. Поменялся только тип результата: был int, стал `Decimal`.

Ревью делалось только для одного модуля. Оплата, часовые пояса, одновременные запросы не проверялись, их в этом проекте нет.
